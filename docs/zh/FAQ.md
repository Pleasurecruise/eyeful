# 常见问题

关于 eyeful 审查什么的几个常见问题，这里给出简短的回答。每条回答都链接到负责相应规则的文档。

## 到底审查的是什么？

审查的是一个快照：一个基准提交，加上一个装着被审查代码的提交。每次审查在运行任何东西之前先固定快照，并把它和发现保存在一起。

在本地，快照取自命令启动时所在的仓库。默认是未提交的改动（已暂存、未暂存和未跟踪的文件）相对 `HEAD`；`--base` 改为相对合并基点比较，`--head` 审查某个提交或分支。未提交的改动不需要用户先提交：eyeful 把它们记成一个没有任何分支指向的提交。本地模式从不审查 pull request。见[可以审查什么](LOCAL.md#what-can-be-reviewed)和[快照](LOCAL.md#snapshot)。

在云端，审查对象总是 pull request，每次推送都是一个新的快照（见[云端运行](CLOUD.md#what-can-be-reviewed)）。

## 改动太大怎么办？

本地和云端的处理完全相同。分诊把 diff 超过 512 KB 的文件放到一边。剩下的文件改动超过 2000 行时，由 Go 按目录拆成每个不超过 2000 行的范围，每个范围单独规划、单独审查，各分一份预算。拆分写在代码里，不靠提示词，所以同样的改动总是得到同样的范围。报告按顺序列出这些范围，作者可以据此把改动拆成一组 stacked 改动；eyeful 自己从不创建分支或 pull request。见[大改动](PLANNER.md#large)。

## 审查期间文件被改动了怎么办？

eyeful 审查的代码不会变，因为快照已经先固定下来了。其余情况取决于是谁改的：

| 谁改的                          | 结果                                                                                                                               |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 用户在工作区里改                | 项目命令不受影响，它们在 eyeful 自己的快照检出里运行。agent 读的是工作区，所以审查结束时 eyeful 会重新取快照比较，不同就给出提示。 |
| 项目命令，比如 `setup`          | 它在 eyeful 的检出里运行，每次运行后恢复原状，审查结束时删除（见[本地审查的步骤](LOCAL.md#how-a-local-review-runs)）。             |
| agent                           | 它的命令行工具只带只读工具运行（见 [agent](LOCAL.md#agents)）。如果文件仍然被改动，审查结束时的检查会给出提示。                    |
| pull request 有新的推送（云端） | 那是新的快照和一次新的审查；正在运行的审查在原来的快照上跑完。                                                                     |
