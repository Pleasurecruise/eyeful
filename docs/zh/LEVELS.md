# 层级

现在每次审查的方式都一样：规则给改动分类，规划器给它分组，每个组需要的专家来审查，发现的问题再经过验证。下面那些更便宜的层还在规划中。

## 谁决定看得多细 {#choosing-the-level}

没有人挑选层级。模型在三个地方做决定：

- 规划器把出错代价最大的组标为核心组。核心组会得到 correctness、skeptic、security 和 design 四个专家（见[计划](PLANNER.md#the-plan)）。
- 每个专家读完改动对自己文件做的所有事，并报告发现的每一个问题。
- 每个专家给自己的发现定级。`error` 和 `warning` 的发现会被验证，`note` 的发现折叠进 nitpick（见[审查反馈](REPORT.md#ranked-report)）。

## 预算 {#budget}

审查有一个按 token 和金额计的预算，验证器运行的每条命令各有超时。总时长没有上限。token 指新输入、输出和缓存写入。agent 从服务商缓存里读回的 token 单独记录，不计入预算；agent 每多走一轮它就多一截，所以一次审查的账单高于它的 token 数。

- Go 在启动每个 agent 之前检查预算，所以正在运行的 agent 仍会跑完。
- 规划器和专家最多用四分之三，其余留给验证。
- 最多四个专家同时运行（见[本地运行](LOCAL.md#agents)）。
- 预算用完后审查不再启动 agent，返回已经验证的部分，结果为 `partial`。

## 规划中的各层 {#planned}

计划是：只有更便宜的检查发现了问题，才启动 agent：

| 层  | 会运行                                                                                                | 模型开销 |
| --- | ----------------------------------------------------------------------------------------------------- | -------- |
| L0  | CI 检查、分拣和文件类型                                                                               | 无       |
| L1  | `lint`、`typecheck`、`secret_scan`、`dependency_audit`、`openapi_diff`、`complexity`、`coverage_diff` | 无       |
| L2  | 规划器、readability 专家、把工具输出变成评论                                                          | 少       |
| L3  | 其余专家，以及复现                                                                                    | 最多     |

目前只有 L0。按工具输出路由会随第一个 L1 工具一起实现，同时测量它相对完整专家组损失了什么（见[评估](EVALUATION.md#ablations)）。
