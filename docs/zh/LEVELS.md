# 档位

一次审查的花费应该和改动的大小相称。现在每次审查都按同一种方式运行：规则给改动分类，规划器给它分组，每个分组需要的专家来审查，它们的发现再被验证。看得多仔细交给模型决定，能花多少由预算决定。这个页面原先描述的更便宜的审查方式（按工具输出路由，以及 quick 档）还在计划中，代码里没有。

## 谁决定看得多仔细 {#choosing-the-level}

没有人选择档位，也没有按改动大小选档的规则，就像 revmux 默认只跑一个配置而不是询问用户。看得多仔细交给模型，体现在三处：

- 规划器把出错代价最高的分组标为核心组，项目也可以用 `.eyeful/config.yml` 里的 `risk` 路径追加。核心组不论属于哪一类，都会派 correctness、skeptic、security 和 design 专家（见[审查计划](PLANNER.md#the-plan)）。
- 每个专家要读到看清这次改动对自己的文件做了什么为止，并报告找到的每一个问题，不论大小。没有任何东西要求它略去什么。
- 每个专家给自己的发现定严重度。`error` 和 `warning` 的发现会被验证并单独展示；`note` 的发现不改变任何行为，不做验证，在报告末尾折叠成 nitpick（见[审查反馈](REPORT.md#ranked-report)）。

## 预算

一次审查有 token 和费用两项预算，验证器执行的每条命令也各有超时。总时长不设上限，因为项目自己的测试可能比任何固定上限都慢。Go 在启动每个 agent 之前检查预算，所以预算用完时已经在跑的 agent 会跑完。规划器和专家最多用掉预算的四分之三，剩下的留给验证和汇总，这样专家读了很多代码的审查仍然能验证它们的发现；同一时间最多运行四个专家，这限制了它们能超出多少（见[本地运行](LOCAL.md#agents)）。此后审查不再启动新的 agent，返回已经验证的部分，结果为 `partial`。

## 计划中：专家之下的几层 {#planned}

每次改动都把所有专家跑一遍，做法简单但开销大，而 linter 或依赖审计本来就能抓到不少问题。计划是只在更便宜的检查发现了问题时，才启动相应的 agent：

| 层级 | 将要运行                                                                                              | 模型开销 |
| ---- | ----------------------------------------------------------------------------------------------------- | -------- |
| L0   | CI 校验、分诊、匹配 `risk` 路径和文件类型                                                             | 无       |
| L1   | `lint`、`typecheck`、`secret_scan`、`dependency_audit`、`openapi_diff`、`complexity`、`coverage_diff` | 无       |
| L2   | 规划器、readability 专家、把工具输出整理成评论                                                        | 小       |
| L3   | 其余专家，以及复现验证                                                                                | 最大     |

L0 已经有了。L1 的工具一个都还没实现，所以 `workflow` 里没有任何东西在等它们的输出：早先的版本带着只审查工具标出内容的 quick 档、把工具命中交给专家的规则，以及必须有工具命中支持的证据类型，因为没有任何一次审查能走到这些路径，它们全部删掉了。等第一个工具真正运行起来时再加回来，同时测量按工具路由比运行有规划的专家组少发现了什么（见[评测](EVALUATION.md#ablations)）。
