# 八条原则

这八条原则是作者自己对工作习惯的总结，用来提醒自己，不是审查的依据。审查怎么做，以[参考文献](REFERENCES.md)中列出的公开文献为准，主要是 Google 的[代码评审指南](https://google.github.io/eng-practices/review/)和 [Conventional Comments](https://conventionalcomments.org)。原则和文献说法不一致时，以文献为准。

| 原则         | 开发时                                           | 审查时                                                                                                        |
| ------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 第一性原理   | 改代码之前，先复现问题、找到原因                 | 阻塞性的发现要有一个修复前失败、修复后通过的测试，[判定依据](VERIFICATION.md#oracle)不能只是 agent 自己的理解 |
| 对抗式审查   | 由没参与实现的人去找反例                         | 专家不是改动的作者，测试结果只由验证器记录                                                                    |
| 消融实验     | 去掉某部分后没有可测量的变化，就删掉它           | 专家和阶段只有在[效果评测](EVALUATION.md#ablations)证明有用时才保留                                           |
| 奥卡姆剃刀   | 先做能用的最小版本，有了需要再加结构             | [档位](LEVELS.md)：先跑规则和工具，有需要时才调用模型                                                         |
| 不自信清单   | 每次交接都写明哪些没有证据、哪些没测、哪些是猜测 | 每份报告最后列出缺席的专家、没能复现的发现和没有运行的项目                                                    |
| 独立思考     | 先各自得出结论，再拿来比较                       | 专家之间看不到彼此的输出，所以两个专家结论一致可以算作互相印证                                                |
| 批判性思维   | 解释得再完整也可能是错的，要说出什么能推翻它     | 每个发现都写明[证据类型](VERIFICATION.md#evidence-kinds)                                                      |
| 高内聚低耦合 | 划好边界，让每部分需要哪些上下文一目了然         | 每个 agent 只拿到分给它的文件、它的检查清单和审查计划                                                         |
