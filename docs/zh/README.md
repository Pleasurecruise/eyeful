# eyeful 是什么

eyeful 用一组 agent 审查代码改动。规划器挑出改动需要的专家，专家对照公开标准并行审查并报出发现的问题；之后 eyeful 让另一个 agent 为每个报出的 bug 写测试，并运行它。结果以评审意见的形式交给人。

```mermaid
flowchart LR
    change(["改动"]) --> plan["规划<br/>CI、分诊、计划"]
    plan --> experts["专家<br/>并行审查"]
    experts --> verify["验证<br/>写测试并运行"]
    verify --> feedback(["评审意见"])
```

## 当前进度

本地审查已经可用：`eyeful review`、`provider`、`connect`、`commit` 和桌面端用你自己的编码 agent 跑完整个流程（见[本地运行](LOCAL.md)）。评测工具已经写好，并做过一次试点（见[效果评测](EVALUATION.md#pilot)）。云端审查（pi 中的 agent、沙箱）、L1 工具和各专家自己的工具还在计划中，相关页面都会注明，顺序见[版本路线图](ROADMAP.md)。

## 局限 {#limits}

eyeful 像读代码的人那样审查改动，并通过运行代码来证明它能证明的部分。它做不到更多：

- 它不是测试工具。它只为自己的发现写复现测试，每条发现一个；它运行的测试套件只有项目自己的那一套，用来看改动弄坏了什么，以及确认修复建议没有弄坏别的东西。它不生成测试套件，不统计覆盖率，也不替代 CI（见[与 CI 的关系](VERIFICATION.md#relation-to-ci)）。
- 它看不到运行中的界面。usability 专家对照 WCAG 和可用性启发式读标记和组件代码；没有任何东西去渲染页面，所以布局错乱、颜色看不清、交互别扭这类问题找不出来。会打开页面的 `a11y_check` 和 `e2e_run` 还在计划中（见[专家](EXPERTS.md#usability)）。
- 它只能找到模型在改动的文件里注意到的问题。一次审查没有发现，不能说明改动是对的；同一个改动审查两次，结果也可能不同。它到底能找到多少，由[效果评测](EVALUATION.md)来衡量。
- 它只报这次改动引入的问题。基础提交上本来就有的缺陷不报，只在仓库之外才显现的问题也不报：其他服务、配置、线上数据和负载。
- 它只能证明单元测试规模的测试能说明的问题。涉及性能、线程间时序，或者需要数据库、浏览器才能出现的行为，这类发现只由评判 agent 读代码，不会运行；没有测试命令的项目完全不做执行验证（见[证据与验证](VERIFICATION.md)）。目前还没有负责性能的专家。
- 它不批准也不合并改动。阻塞评论只是给做决定的人的建议（见[一次审查的全过程](REVIEW.md#rules)）。
- 在用户电脑上，它的 agent 以该用户的身份运行，没有沙箱（见[本地运行](LOCAL.md)）。
