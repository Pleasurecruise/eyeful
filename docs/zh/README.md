# 概览

eyeful 用一组 agent 审查代码改动。规划器给改动分组，每个组需要的专家并行审查。eyeful 找到项目的测试命令时，会让 agent 为每个报告的 bug 写一个测试并运行它；找不到时由 judge 阅读这些发现。结果以审查评论的形式交给人。

```mermaid
flowchart LR
    change(["改动"]) --> plan["规划<br/>CI、分拣、计划"]
    plan --> experts["专家<br/>并行"]
    experts --> verify["验证<br/>编写并运行测试"]
    verify --> feedback(["审查评论"])
```

## 现状

- **可用：** 本地审查。`eyeful review`、`provider`、`connect`、`commit` 和桌面应用用你自己的编码 agent 运行完整的工作流（见[本地运行](LOCAL.md)）。
- **进行中：** 评估。工具已经写好，实验还没有运行（见[评估](EVALUATION.md)）。云端审查在 GitHub Actions 的 job 里逐个处理 pull request，并在每次审查的沙箱容器里验证（见[云端运行](cloud/CLOUD.md)）。
- **规划中：** L1 工具和专家自己的工具（见[路线图](ROADMAP.md)）。

## 局限 {#limits}

- **它不是测试工具。** 它为每条发现写一个测试，并运行项目自己的测试套件。它不生成测试套件，也不统计覆盖率（见[与 CI 的关系](VERIFICATION.md#relation-to-ci)）。
- **它看不到运行中的界面。** usability 专家阅读标记和组件代码，没有任何东西渲染页面（见[专家](EXPERTS.md#usability)）。
- **没有发现的审查什么都证明不了。** 它找到的是模型在改动文件里注意到的东西，同一个改动的两次审查可能不同。
- **它只报告改动引入的问题。** 基准提交原本就有的缺陷，以及仓库之外的一切，都不在范围内。
- **它只能证明单元大小的测试能证明的东西。** 性能、线程间的时序、需要数据库或浏览器的行为由裁判阅读，从不运行。
- **它不批准也不合并**（见[一次审查](REVIEW.md#rules)）。
- **本地没有沙箱。** 它的 agent 以用户身份运行（见[本地运行](LOCAL.md)）。
