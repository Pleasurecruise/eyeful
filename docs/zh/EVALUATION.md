# 评估

本页定义毕业设计的实验，并记录它的结果。工具在 `eval/` 里，试点已经运行过。完整的数据集、标注和主实验还没有做（见[路线图](ROADMAP.md)）。

**试点目前能支持的结论：** 在公开的 pull request 上，专家组比单个 agent 找到更多已知问题，token 约为三倍。在八个注入缺陷上，专家组报出了全部八个，其中五个走完了所有关卡，判定依据规则只让一个成为阻塞。还没有任何标注，所以精确率未知。

## 研究问题 {#research-question}

与更简单的 LLM 审查者相比，带规划的多专家审查加上基于执行的验证，能否找到更多要紧的缺陷、噪声更少、并给出维护者可以核对的证据？代价是多少？

| 问题          | 问的是                                                                   |
| ------------- | ------------------------------------------------------------------------ |
| RQ1，检出     | 规划出的专家组是否比使用相同模型和 skill 的单个 agent 找到更多已知缺陷？ |
| RQ2，噪声     | 在每种验证条件下，报告的发现里有多大比例是可采取行动的？                 |
| RQ3，可验证性 | 执行能确认多少发现，漏掉多少真实缺陷，代价是多少？                       |

## 配置与条件

配置决定谁来找问题，条件决定发现怎样被验证。

| 配置   | 运行方式                   | 谁来审查                                                       |
| ------ | -------------------------- | -------------------------------------------------------------- |
| panel  | `eyeful review`            | 规划器给改动分组，Go 挑选专家                                  |
| single | `eyeful review generalist` | 一个拥有全部 skill 的 agent（见[名册](EXPERTS.md#the-roster)） |

| 条件      | 验证方式                                      |
| --------- | --------------------------------------------- |
| execution | 验证器运行每个复现，没有复现的发现由裁判阅读  |
| read-only | [裁判](VERIFICATION.md#the-judge)阅读每条发现 |
| none      | 发现按专家写的原样报告                        |

三种条件在同一份发现存档上运行，所以唯一的差别就是验证。revmux 在同样的被试上运行，作为外部参照而不是基线：它的提示词和拆分方式不同。

## 数据集

一个被试是一个缺陷已知的改动。

| 数据集                     | 规模     | 作用                                                                           |
| -------------------------- | -------- | ------------------------------------------------------------------------------ |
| 注入缺陷                   | 约 60 个 | 主要数据集。来自模型训练截止之后创建的仓库的真实提交，每个放入一个缺陷         |
| SWE-bench Verified，回退版 | 约 30 个 | 次要数据集。基准包含参考修复，改动把它去掉                                     |
| Code Review Bench，离线    | 50 个    | 外部数据集。五个项目的 pull request，带 173 个人工审查者确认的问题。不运行测试 |
| ReviewBench                | 219 个   | 外部数据集，也是 eyeful 开发时对照的数据集。187 个仓库、19 种语言。不运行测试  |

ReviewBench 的 25 个测试 pull request 在改 harness 时使用，留出一部分只在每次改动后检验一次，全集留给最后一次运行。

- 数据集放在 `.eval/` 下，被 git 忽略。
- SWE-bench 被试用任务自带的 Docker 镜像构建，镜像名是中性的，issue 文本不提供。测试在没有网络的全新容器里运行。
- 被试的描述指明了缺陷，它和仓库分开存放，每次审查都在只能读取该仓库的沙箱里运行。早先的布局让 agent 能读到描述，那样做出的比较全部作废。

## 流程

每个被试在每种配置和每种条件下各审查三次。模型、提示词、预算和这份分析计划在主实验开始前固定。

## 标注 {#labelling}

已知缺陷不需要标注：一条发现落在缺陷所在的文件上、距改动行三行以内就算命中。其余的由作者标注，每条不同的发现标一次。

三点都成立时，一条发现才是**可采取行动的**：

1. 问题确实以发现描述的方式存在于改动的代码里；
2. 是这次改动引入或暴露的；
3. 它改变了可观察的行为，或违反了明文约定。

其余都是**噪声**。裁判用的是同样的三点。

标注表以固定的随机顺序展示发现，不显示工具、配置和验证结果。五分之一的发现至少两周后再标一次，报告两次之间的 Cohen's κ。只有一位作者标注，这是效度上的威胁。

## 指标与分析

| 问题 | 指标                                                                                          | 分析                         |
| ---- | --------------------------------------------------------------------------------------------- | ---------------------------- |
| RQ1  | 召回率：已知缺陷被报告的被试比例；CWE 类别；每 token 的检出数                                 | 配置之间的 McNemar 精确检验  |
| RQ2  | 可采取行动的精确率，A / (A + N)                                                               | 以被试为单位的配对 bootstrap |
| RQ3  | 可验证率：通过全部六道关卡的复现。验证损失：执行没能确认的可采取行动的发现。token、费用、秒数 | 以被试为单位的 bootstrap     |

每个估计值都带 95% 区间，来自对整个被试的 10,000 次重采样。

## 消融实验 {#ablations}

去掉后测不出变化的部分，就从 eyeful 里去掉。

| 去掉的部分     | 运行方式                             | 预期效果                           |
| -------------- | ------------------------------------ | ---------------------------------- |
| 规划器         | `eyeful review correctness security` | 混合改动上的召回率下降，或没有变化 |
| 判定依据的核对 | 从存档计算                           | 更多发现成为阻塞，它们的精确率下降 |

专家独立性就是这样检验后去掉的：让专家一个接一个运行，找到的一样多，耗时却是两倍（见 [Code Review Bench](#crb-pilot)）。

## 工具 {#tooling}

`eval/` 里的脚本只用 Python 标准库，`plot.py` 和 `score.py` 除外，它们用 `uv run` 运行。`mise run test` 会运行它们的测试。

| 脚本             | 作用                                                                                                                                                                       |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inject.py`      | 筛选仓库，挑选真实提交，并给每个提交放入一个缺陷                                                                                                                           |
| `subjects.py`    | 从 SWE-bench 的行、注入规格或 Code Review Bench 的 golden comment 构建被试                                                                                                 |
| `run.py`         | 用 eyeful 审查每个被试：每种配置先找问题，然后各种条件做验证                                                                                                               |
| `revmux.py`      | 用 revmux 审查每个被试                                                                                                                                                     |
| `confine.py`     | 在 macOS 沙箱里启动 pi，它只能读被审查的仓库，读不到用户的其他东西                                                                                                         |
| `audit.py`       | 列出审查者的 agent 在仓库之外打开过什么；有这种情况的审查记为 `leaked`                                                                                                     |
| `match.py`       | 按 Code Review Bench 离线流程的方式给审查打分                                                                                                                              |
| `reviewbench.py` | 准备 ReviewBench 被试，并把 eyeful 的评论写成基准的输入格式。`table` 每次审查写一行；`standing` 在裁判评过分的每个 pull request 上给一次运行打分，只算每份报告的前几条评论 |
| `score.py`       | 用 [Jev](ARCHITECTURE.md#jev) 把 eyeful 的评论和 ReviewBench 的 golden 发现配对，按 `table` 和 `standing` 读取的格式写出 grounded 分数                                     |
| `plot.py`        | 把 eyeful 画在 ReviewBench 排行榜旁边                                                                                                                                      |
| `label.py`       | 写出盲标注表并计算 κ                                                                                                                                                       |
| `analyze.py`     | 根据审查和标注计算各项指标                                                                                                                                                 |

## 试点 {#pilot}

### Code Review Bench，七个 pull request {#crb-pilot}

设置：2026 年 10 月 12 日，七个 pull request（Cal.com 三个、Sentry 两个、Grafana 两个，共 37 条 golden comment），在沙箱里，每种配置运行一次，所有 agent 和匹配裁判都是 pi 上的 `opencode-go/deepseek-v4.1-flash`。每条发现都由裁判阅读。

| 审查者                          | 召回率           | 每次审查的发现数 | Token（千） | 秒    |
| ------------------------------- | ---------------- | ---------------- | ----------- | ----- |
| eyeful 专家组，层级还决定深度时 | 0.65（31 中 20） | 13               | 472         | 486   |
| eyeful 专家组                   | 0.86（37 中 32） | 25               | 578         | 696   |
| eyeful，专家一个接一个          | 0.84（25 中 21） | 20               | 796         | 1,598 |
| revmux `pi-only`                | 0.65（37 中 24） | 6                | 422         | 630   |
| **eyeful 专家组，留出集**       | 0.75（20 中 15） | 16               | 517         | 645   |

- 第一行只覆盖其中五个 pull request，第三行覆盖四个。
- **应该引用的数字是 0.75。** 那七个 pull request 正是调整提示词时用的。最后一行是没有任何运行碰过的七个 Cal.com pull request，在什么都没改的情况下审查了一次。
- 每个只运行一次，一两条 golden comment 的差别属于噪声。
- 把深度交给专家决定，是召回率从 0.65 升到 0.86 的原因。
- 专家之间重叠很多：找到的 32 条 golden comment 里，21 条由不止一个专家报告。只有一个专家报告的：tests 4 条、skeptic 3 条、design 2 条、correctness 1 条、security 1 条。
- 专家一个接一个运行，找到的一样多，耗时是 2.2 倍。
- 一个裁判一起读一个组的发现，用的 token 是每条发现一个裁判时的 55%，67 个结论里有 62 个和之前一样。
- 没有任何标注，所以没有精确率。

### ReviewBench，测试用的 pull request {#reviewbench-pilot}

设置：2026 年 10 月 12 日，25 个测试 pull request，每种配置审查一次，所有 agent 都用 `opencode-go/deepseek-v4.1-flash`，由基准的裁判用 `deepseek-v4-flash` 评分，代替 Claude Sonnet 5。两个模型账户都用完了：有十个 pull request 两种配置都有分数。

| 审查者          | Grounded recall | Grounded precision | 每个 pull request 的评论数 | Token（千） |
| --------------- | --------------- | ------------------ | -------------------------- | ----------- |
| eyeful 专家组   | 0.41            | 0.82               | 16.0                       | 590         |
| eyeful 单 agent | 0.25            | 0.79               | 6.2                        | 190         |

- 十个里有七个，专家组找到的 golden finding 比单 agent 多，没有一个更少。
- 这个裁判偏宽松：专家组 104 条没有匹配上的评论里，它把 93 条判成了真问题。
- 评论的排序在顶部是可靠的：前五条有 55% 匹配 golden finding，第六到第十条 25%，其余 15%。
- 一致性能预测匹配：两个或更多专家报告的评论 62% 匹配，单个专家的 19%。
- 裁判有异议的 11 条评论没有一条匹配 golden finding。
- nitpick 占 160 条评论里的 76 条，其中 16% 匹配。
- 相对单 agent 的提升在中、低严重度的发现上（0.55 对 0.38，0.27 对 0.09）。高严重度的发现，专家组找到 11 条里的 5 条，单 agent 找到 6 条。

### ReviewBench，`dbf9e50` 上的测试集 {#reviewbench-dbf9e50}

设置：2026 年 10 月 12 日至 13 日，同样的 25 个 pull request，用提交 `dbf9e50` 构建的二进制，同样的模型。专家组审查了全部 25 个，其中两个是 `partial`，因为最大的两处改动用完了预算。单 agent 在触及服务商上限前审查了 20 个。每次审查在 [`reviewbench-test.csv`](/eval/reviewbench-test.csv) 里占一行，`before` 的行是此前那次试点。

**成本。** 在两次运行都审查过的 pull request 上：

| 每次审查            | Pull request 数 | 评论数 | Token（千） | 秒  |
| ------------------- | --------------- | ------ | ----------- | --- |
| 专家组，此前        | 21              | 16.4   | 592         | 698 |
| 专家组，`dbf9e50`   | 21              | 20.5   | 647         | 581 |
| 单 agent，此前      | 19              | 6.5    | 186         | 409 |
| 单 agent，`dbf9e50` | 19              | 7.8    | 185         | 404 |

在两种配置都完成的 20 个 pull request 上，专家组读的内容是单 agent 的 3.2 倍：

| 每次审查的 token（千） | 专家 | 裁判 | 规划器 | 合计 |
| ---------------------- | ---- | ---- | ------ | ---- |
| 专家组                 | 435  | 130  | 24     | 589  |
| 单 agent               | 129  | 54   | 0      | 183  |

改动大一百倍，专家组的成本大约是十倍。

### 注入缺陷，八个被试 {#injected-pilot}

设置：2026 年 10 月 13 日，目前已构建的八个被试，来自四个 Python 仓库：三个边界错误、两个缺少检查、两个条件写错、一个资源泄漏。运行在沙箱里，专家组对每个被试审查一次，二进制由 `790aefb` 构建，所有 agent 都用 `volcengine/deepseek-v4.1-flash`。三种条件共用同一批发现。pi 传了 `--thinking off`，但模型在多数轮次里仍然在推理，本页所有运行都是如此。

| 已知缺陷的结果                             | 被试数   |
| ------------------------------------------ | -------- |
| 被报出                                     | 8 个全部 |
| 被复现、确认是引入的、修复通过且没弄坏别的 | 5        |
| 复现停在 `introduced`，由裁判确认          | 1        |
| 复现停在 `introduced`                      | 1        |
| 只被报成 `note`，所以没有被验证            | 1        |
| 显示为 `issue (blocking)`                  | 1        |

- 一共写了十三个复现。全部能运行、五次结果一致、并按声称的方式失败。九个通过了其余关卡，四个停在 `introduced`。每一个要求的修复都通过了验证：九个里九个。
- 四次停下里有三次在同一个被试上，它的改动新增了被测文件。它的测试在基准提交上也失败，关卡据此判为原本就有，而这个缺陷已知是改动带来的。原因还没有查清。
- 能不能阻塞由判定依据规则决定。走完全部关卡的五个缺陷里，一个的判定依据是 `specified`，成为阻塞；其余是 `human`（2 个）和来自新测试的 `derived`（2 个），成为 question。
- 这些审查共产生 27 条评论：13 条 question、13 条 nitpick、1 条 issue。都还没有标注。
- 执行条件下一次审查用 31.9 万 token、408 秒，不做验证时是 19.9 万和 238 秒。专家占 token 的 58%，复现占 32%。每次审查另外从缓存读了 250 万 token。
- 八个被试各审查一次，只说明这条链路能走通，不构成估计。
- `analyze.py` 逐条统计发现，而被合并为同一个问题的发现没有自己的验证结论，所以它在这里给出的可验证率和损失偏低。上表是按已知缺陷从各个 `result.json` 里数出来的。TODO(eval)：按问题统计。

### Jev，在已存档的审查上 {#jev-pilot}

设置：2026 年 10 月 13 日，`jev-1.13.0`，在 `dbf9e50` 上 25 次专家组审查（748 条发现）的存档输出上提问。没有重新运行任何审查。

| 判断                                        | 对比对象             | 结果                                               | 由谁决定                   |
| ------------------------------------------- | -------------------- | -------------------------------------------------- | -------------------------- |
| 两行以内的两条发现是同一个问题，318 对      | 人工读过的 35 对     | 204 对在 0.9 及以上，80 对低于 0.2；样本一致       | Jev                        |
| 一条评论说的是某条 golden 发现，2,498 对    | 基准的裁判           | 98.3% 的对结论相同；找到 115 条 golden，裁判是 117 | Jev，在 harness 变动期间   |
| 裁判的三点标准，只看文件的 diff，314 条发现 | 裁判的结论           | 裁判驳回的 26 条里认出 4 条；AUC 0.69              | 裁判：调用方不在 diff 里   |
| 严重度，只看发现的文字，376 条评论          | 是否命中 golden 发现 | AUC 0.73，专家是 0.71                              | 专家                       |
| 评论所属的领域，376 条评论                  | 报告它的专家的领域   | 299 条落在其中                                     | 专家的领域                 |
| 文件的类别，245 个文件                      | 规划器的分组         | 72% 类别相同，80% 选出的专家相同                   | 规划器：它仍要分组和写摘要 |

- 只按位置合并时，有 97 对不同的问题被合并。用 Jev 后 748 条发现变成 589 条评论，按位置是 569 条。
- `score.py` 和基准的裁判一致（19 个 pull request 上 r = 0.99），但不给没有匹配的评论分类，所以要引用的数字仍然来自基准的裁判。
- 0.5 是在看结果之前定的，而且每个数字都来自 eyeful 开发时用的那些 pull request。
