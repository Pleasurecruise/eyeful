# 效果评测

本页属于毕业设计，定义了回答研究问题的实验，实验结果也是对外公布的 eyeful 数据。实验在 v1.0 的研究核心上进行，在开发其他客户端之前完成（见[版本路线图](ROADMAP.md)）。工具放在 `eval/` 下，已经在 SWE-bench 的被试上做过一次试点（见[试点](#pilot)）；完整的数据集、标注和主实验还没有做。

## 研究问题 {#research-question}

目标是确定：和更简单的 LLM 审查方式相比，带规划的多专家审查加上执行验证，能不能找到更多真正要紧的缺陷，噪声更少，并且给出维护者可以核对的证据；代价又是多少。问题只针对 correctness 和 security 的发现，因为只有它们能够复现：

| 问题          | 问的是什么                                                                            |
| ------------- | ------------------------------------------------------------------------------------- |
| RQ1，检出     | 用同样的模型和 skill，带规划的专家组是否比单个 agent 找到更多已知缺陷、更多类别的问题 |
| RQ2，噪声     | 每种验证条件下，报告出来的发现里有多大比例是可采取行动的                              |
| RQ3，可验证性 | 执行验证能确认多少发现，漏掉多少真实缺陷，花费多少 token、多少钱、多少时间            |

RQ2 不预设方向。如果只读验证留下的发现本来就大多可采取行动，执行验证的价值就落在 RQ3：给出的是一个失败的测试和一个测过的修复，而不是一段论证。

## 配置与条件

实验改变两样东西：配置决定由谁来找问题，条件决定怎样验证发现。

| 配置   | 运行方式                   | 谁来审查                                                                  |
| ------ | -------------------------- | ------------------------------------------------------------------------- |
| panel  | `eyeful review`            | 规划器给改动分组，Go 选专家                                               |
| single | `eyeful review generalist` | 一个 agent，带着各专家的全部 skill（见[专家名单](EXPERTS.md#the-roster)） |

| 条件      | 验证方式                                                                                                  |
| --------- | --------------------------------------------------------------------------------------------------------- |
| execution | 验证器让每个复现测试依次通过各道[关卡](VERIFICATION.md#the-verifier)，没有复现测试的发现由裁判 agent 来读 |
| read-only | 由[评判 agent](VERIFICATION.md#the-judge) 读代码和每条发现，给出结论                                      |
| none      | 不验证，按专家写的原样报告                                                                                |

每次审查通过 `Request.Verification` 选择条件：`execution`、`read_only` 或 `none`。运行存档里，验证器的输出按条件名分开保存，在它们之前的内容只保存一份，所以在同一份存档上跑三种条件时，用的是同一份计划和同一批发现，只有验证不同。专家在 `execution` 条件下找问题，因为只有这时它们才知道复现命令，才会提交测试。

revmux 的验证阶段也是只读的，它会在同样的被试上运行，作为外部参照，但不作为基线：它的提示词和切分方式与 eyeful 不同，这些差异会混进结果里。

## 数据集

一个被试是一次改动，形态和 pull request 相同，里面的缺陷是已知的。

| 数据集                    | 规模     | 用途                                                                                                                                                                                                                                                                                                                 |
| ------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 注入缺陷集                | 约 60 个 | 主要数据集。取模型训练截止日期之后创建的仓库里的真实提交，每个注入一个固定类型的缺陷：边界错误、缺少检查、条件写错、资源泄漏或注入漏洞                                                                                                                                                                               |
| SWE-bench Verified 回滚集 | 约 30 个 | 次要数据集。基础提交里带着参考修复，改动把它去掉。单独报告，因为模型可能见过这些仓库                                                                                                                                                                                                                                 |
| Code Review Bench 离线集  | 50 个    | 外部数据集。Sentry、Grafana、Cal.com、Discourse 和 Keycloak 的真实 pull request，每个都带着人工审查确认过的问题，共 173 条。一个 pull request 里有多个问题，所以它能衡量一次审查覆盖了改动的多少，这是每个被试只有一个缺陷的数据集做不到的。这些仓库里不运行测试，所以每条发现都靠读代码评判                         |
| ReviewBench               | 219 个   | 外部数据集，也是 eyeful 开发时对照的数据集。来自 187 个仓库、19 种语言的公开 pull request，每个都带着 GitHub 这个基准认定为真或假的发现，平均每个 pull request 约十二条真的。其中 25 个测试 pull request 在改 harness 时使用，其余的留出一部分只在每次改动后检验一次，全集留给最后一次运行。这些仓库里同样不运行测试 |

数据集都放在仓库里的 `.eval/` 下，git 忽略这个目录：每个数据集一个目录，里面是基准自己的文件、被试的描述、目录名不透露任何信息的仓库，以及运行记录和评分。评测的任何东西都不放在用户主目录或临时目录里。

SWE-bench 的被试从任务自带的 Docker 镜像构建。改动的提交信息只写文件名，不提供 issue 原文，镜像另起一个中性的名字，所以仓库里没有任何东西能看出这是哪个任务。项目命令每次都在一个没有网络的新容器里、对检出的一份副本运行测试；回归测试集取该任务的 pass-to-pass 测试中在这种环境下能通过的那些。构建脚本支持用 pytest 或 Django 测试运行器的项目。

审查者能读到改动之外的东西，就等于带着答案审查。被试的描述里写着缺陷所在的行，它和被试的仓库分开存放；每次审查的 agent 都在沙箱里运行，只能读这个仓库，也不能启动会下载东西的程序。早先的布局把描述放在仓库旁边，agent 读了它、读了别的运行结果，有 shell 的还下载了项目后来的发行版；那样得到的对比全部作废。

## 流程

实验采用被试内设计：每个被试在每种配置、每种条件下都审查一遍，这样被试之间难度的差异就不会影响比较。因为模型的输出每次都不一样，每种配置对每个被试审查三次，每次存档下来的发现再分别经过三种条件。模型、提示词、单次审查的预算和这份分析计划，都在主实验开始之前定下来。

## 标注 {#labelling}

已知缺陷有没有被找到不需要标注：发现所在的文件就是缺陷所在的文件，行号与缺陷改动的行相差不超过三行，就算找到。审查者报告的其他内容由作者标注，每条不同的发现标一次；同一个文件里相差不超过两行的发现算同一条。

只有同时满足三点，一条发现才标为**可采取行动**：

1. 问题确实存在于改动后的代码里，和发现描述的一致；
2. 是这次改动引入或暴露的，而不是原样留下来的；
3. 它改变了可以观察到的行为，或者违反了明确的约定：issue、文档、API schema 或已有的测试。

其余都是**噪声**：风格、命名和措辞；说不出哪个输入或哪种顺序会出错的担忧；原本就有的问题；代码已经遵守的约定被重复了一遍。评判 agent 用的是同样的三点，所以各条件的差别在证据，而不在对缺陷的定义。

标注表按固定的随机顺序列出每条发现所属的被试、位置和文字，不显示它来自哪个工具、哪种配置，也不显示验证结果。五分之一的发现在至少两周后再标一次，用两次之间的 Cohen's κ 报告标注者自身的一致性。导师同意的话，再抽一部分由另一人独立标注。只有一名作者标注是对有效性的威胁，论文会说明这一点。

## 指标与分析

| 问题 | 指标                                                                                                                       | 分析                         |
| ---- | -------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| RQ1  | 召回率：已知缺陷被报告的被试所占比例；找到的 CWE 类别数；每百万 token 的检出数                                             | 配置之间做 McNemar 精确检验  |
| RQ2  | 每种条件报告的内容里的可行动精确率 A / (A + N)                                                                             | 以被试为单位的配对 bootstrap |
| RQ3  | 可验证率：通过全部六道关卡的复现所占比例。验证损失：可采取行动的发现里执行验证没能确认的比例。每次审查的 token、费用和秒数 | 以被试为单位的 bootstrap     |

每个估计值都带 95% 区间，来自对整个被试做 10,000 次重采样。除了单人标注，对有效性的威胁还有注入缺陷够不够真实，以及被试覆盖了哪些语言。

## 消融实验 {#ablations}

工作流的每个部分都要证明自己有用：去掉它，重新跑一遍，看指标怎么变。

| 去掉的部分   | 运行方式                             | 预期结果                             |
| ------------ | ------------------------------------ | ------------------------------------ |
| 规划器       | `eyeful review correctness security` | 混合型改动的召回率下降，或没有变化   |
| 判定依据评定 | 从存档直接计算                       | 更多发现会阻塞，这些发现的精确率下降 |

去掉之后没有任何可测量变化的部分，就从 eyeful 中删掉。专家互相独立这一点已经这样测过，对应的参数也删掉了：让专家依次运行、每个都能看到前面的发现，召回率不变，耗时是两倍（见 [Code Review Bench](#crb-pilot)）。

## 工具 {#tooling}

`eval/` 里的脚本只用 Python 标准库，`mise run test` 会运行它们的测试。每个脚本都支持 `--help`。

| 脚本             | 作用                                                                                                                                                                                                                                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inject.py`      | 筛选出在普通 Python 镜像里 pytest 测试能通过的仓库，挑选真实提交，并在每个提交里注入一个缺陷                                                                                                                                                                                                                                  |
| `subjects.py`    | 从 SWE-bench Verified 的数据、注入缺陷集的说明或 Code Review Bench 的标准评论文件构建被试。被试的描述写明了缺陷所在，它和审查者工作的仓库分开存放，仓库的目录名不透露任何信息                                                                                                                                                 |
| `run.py`         | 用 eyeful 审查每个被试：每种配置每次重复找一遍问题，再由各条件分别验证。`--pi` 固定每次 pi 调用的模型和思考档位，并记录在审查结果旁边                                                                                                                                                                                         |
| `revmux.py`      | 用 revmux 审查每个被试。`pi-only` 这个 profile 需要带 pi 执行器的 revmux 构建，上游没有                                                                                                                                                                                                                                       |
| `confine.py`     | 在 macOS 沙箱里启动 pi：只能读被审查的仓库和 pi 自己的文件，读不到用户的其他文件；不能修改仓库；读不到 pi 保存的会话和任何已安装的 Python 包；也不能启动 `curl`、`pip`、`python` 和 git 的 HTTP 辅助程序。它给 agent 一个私有的临时目录，以及不读用户配置的 git。`run.py` 和 `revmux.py` 的每次审查都通过它、在临时目录里运行 |
| `audit.py`       | 列出审查者的 agent 在仓库之外打开过的东西，范围是沙箱没有挡住、又不属于系统和工具链的位置；只要有，这次审查就记为 `leaked`                                                                                                                                                                                                    |
| `match.py`       | 按 Code Review Bench 离线流程的做法给它的被试上的审查打分：由模型用基准自带的提示词，把报出的每条发现和这个 pull request 的每条标准评论逐一比对；召回率是匹配上的标准评论数；精确率是同一个数除以发现数，另外也按发现所指的位置算一遍，同几行上的发现只算一处                                                                 |
| `reviewbench.py` | 把 ReviewBench 的 pull request 准备成被试（从基准的镜像仓库拉取），并把 eyeful 对它们的评论写成基准的评判输入格式：默认只交单独展示的评论，加 `--folded` 时连折叠的 nitpick 一起交。之后由基准自带的评判来打分                                                                                                                |
| `label.py`       | 生成盲标表和第二遍的抽样表，并计算 κ                                                                                                                                                                                                                                                                                          |
| `analyze.py`     | 根据审查结果和标注计算上面的指标                                                                                                                                                                                                                                                                                              |

所有数字都来自运行存档：每次审查的运行目录里有快照、diff、每个阶段的检查点（含每次 agent 调用报告的 token 和费用），以及带着每条验证及其各次运行结果的结果文件，`run.py` 从中推出它停在哪道关卡。

## 试点 {#pilot}

试点只是为了确认整套流程能跑通，并不是正式实验；它是在审查进沙箱之前跑的，审查者读得到每个被试的描述，所以它的数字说明不了任何一个工具的能力。它在 2026 年 10 月 11 日进行，用了 18 个 SWE-bench Verified 被试（Requests 6 个、pytest 5 个、Django 3 个、Pylint 3 个、Flask 1 个），按任务编号顺序，从参考修复只改一个文件、且不超过 1,500 字节的任务里选取。每种配置对每个被试只审查了一次，而不是三次。agent 是 Claude Code，所有模型档位都设为 `claude-sonnet-5-5`；revmux 用它的 `claude-only` 配置，模型相同。目前还没有标注，所以没有精确率。

| 审查方式           | 召回率            | 每次审查的发现数  | token（千）    | 秒          |
| ------------------ | ----------------- | ----------------- | -------------- | ----------- |
| eyeful，panel      | 0.83 [0.67, 1.00] | 0.89 [0.67, 1.11] | 89 [81, 98]    | 39 [33, 46] |
| eyeful，single     | 0.67 [0.44, 0.89] | 0.67 [0.44, 0.89] | 58 [50, 67]    | 29 [23, 36] |
| revmux claude-only | 0.94 [0.83, 1.00] | 1.22 [1.00, 1.44] | 326 [291, 368] | 41 [36, 48] |

eyeful 的数字取自 execution 条件。有四个被试专家组找到了缺陷而单个 agent 没找到，有一个反过来（McNemar p = 0.38）；有两个被试 revmux 找到了而专家组没找到（p = 0.50）。在这个规模下，两个差异都不显著。revmux 一次审查读的 token 大约是专家组的 3.7 倍，耗时相当。eyeful 的 28 条发现全部落在已知缺陷上；revmux 的 22 条里有 3 条在别处，和标注表上的 20 条不同发现一起等待标注。

execution 条件下，28 条发现里有 26 条带复现测试。本页的判定依据、严重度和证据类型都按每次运行当时代码里的名字记录；`existing` 和 `base` 现在是 `derived`，`spec` 是 `specified`，`agent` 是 `human`（见[测试预言问题](VERIFICATION.md#oracle)）：

| 指标                                    | 数值                                                   |
| --------------------------------------- | ------------------------------------------------------ |
| 可验证率：通过全部六道关卡              | 0.62 [0.38, 0.82]                                      |
| 其余停在哪一关                          | `fails_as_claimed` 5，`pass_to_pass` 3，`introduced` 2 |
| 已确认发现的判定依据                    | `base` 11，`agent` 7，`implicit` 1                     |
| 有判定依据规则时的阻塞数，以及没有时    | 1，以及 19                                             |
| 已知缺陷上的验证损失                    | 0.32 [0.11, 0.56]                                      |
| token（千）：none、read-only、execution | 80、104、89                                            |

回滚出来的改动不带 issue 原文，所以几乎没有发现能拿到外部的判定依据，判定依据规则把 19 条已确认的复现里的 18 条变成了提问。注入缺陷集的改动带着自己的提交信息，`spec` 才有机会出现。在这里执行验证比评判 agent 便宜，因为评判 agent 要为每条发现重新读一遍代码。停在 `pass_to_pass` 的三条都是因为被试的回归测试集为空，这是构建脚本的局限，和发现本身无关。

“要求修正一次复现”这一步是在这些运行之后加上的，并在同一批存档的发现上试了一遍：五个失败原因和声称不符的复现里，有三个随后按声称的方式运行了；可验证率从 0.62 变为 0.65，已知缺陷上的验证损失从 0.32 变为 0.25。

两项需要重新运行的消融在其中 12 个被试上各试了一次：不用规划器而直接点名专家、专家依次运行，都找到了 12 个缺陷中的 12 个，专家组是 12 个中的 11 个；每次审查大约一条发现、8 万到 8.9 万 token。只有一个缺陷的小改动区分不出它们。

### Code Review Bench，七个 pull request {#crb-pilot}

2026 年 10 月 12 日，基准里的七个 pull request（Cal.com 三个、Sentry 两个、Grafana 两个，共 37 条 golden 评论）在沙箱里各按每种配置审查了一次，所有 agent 和匹配用的评判模型都是 pi 上的 `opencode-go/deepseek-v4.1-flash`。这些仓库里不运行测试，所以每条发现都由裁判 agent 来读。每种配置只跑一次，一两条 golden 评论的差别不超过同一配置跑两次本来就有的出入。

| 审查者                                         | 召回率           | 每次审查的发现数 | Token（千） | 秒    |
| ---------------------------------------------- | ---------------- | ---------------- | ----------- | ----- |
| eyeful 专家组，当时深度还由档位决定            | 0.65（31 中 20） | 13               | 472         | 486   |
| eyeful 专家组                                  | 0.86（37 中 32） | 25               | 578         | 696   |
| eyeful，专家依次运行                           | 0.84（25 中 21） | 20               | 796         | 1,598 |
| revmux `pi-only`                               | 0.65（37 中 24） | 6                | 422         | 630   |
| eyeful 专家组，七个没有用来调过的 pull request | 0.75（20 中 15） | 16               | 517         | 645   |

第一行只有其中五个 pull request，第三行只有四个，专家组在这四个上同样找到 25 条中的 21 条；第三行运行时裁判还不是一次读一个分组（见[裁判](VERIFICATION.md#the-judge)），多出来的 token 大部分来自这里。让召回率变化的是把深度交给专家自己决定。专家组的 25 条发现落在 15 个位置上，每次审查对上 4.6 条 golden 评论；revmux 的 6.3 条发现对上 3.4 条。对不上的位置还没有标注，所以这些数字还说明不了精确率。

专家之间重叠很多：专家组找到的 32 条 golden 评论里，有 21 条不止一个专家报告；只有一个专家报告的，tests 有 4 条，skeptic 3 条，design 2 条，correctness 和 security 各 1 条。专家依次运行找到的一样多，发现数少四分之一，耗时是 2.2 倍。还试过一种折中做法，只让 skeptic 排在其他专家之后并告诉它前面的发现：找到 37 条中的 33 条，token 相同，耗时多三分之一，没有保留，因为一条 golden 评论的差别在噪声之内。

上面七个 pull request 同时也是调整专家提示词时用的，所以 0.86 是开发集上的数字。最后一行是对它的检验：基准里此前任何一次运行都没碰过的七个 Cal.com pull request，全部是 TypeScript，中间不做任何改动，各审查一次。那里的召回率是 0.75，低 11 个百分点；开发集里三个 Cal.com pull request 上是 0.86（21 中 18）。只有 20 条 golden 评论，没法确定地把两者分开，但方向和过拟合一致，对外应当引用 0.75。漏掉的五条评论里，两条是措辞或脚本可移植性问题，三条是功能问题：一个判断条件漏掉了没有团队的组织，一个可空的列没有默认值，一个对象 URL 始终没有释放。留出集只用来测量，不在它上面调整提示词。

### ReviewBench，测试用的 pull request {#reviewbench-pilot}

2026 年 10 月 12 日，基准的 25 个测试 pull request 由专家组和单 agent 各审查了一次，所有 agent 都用 `opencode-go/deepseek-v4.1-flash`，评分用基准自带的评判，模型是 `deepseek-v4-flash`，而不是榜单所用的 Claude Sonnet 5。两个模型账户的额度用完时运行停了下来：有十个 pull request 两种配置都有分数，最大的四个没有审查结果；这次交上去的是全部评论，包括 nitpick。

| 审查者                | 有依据的召回率 | 有依据的精确率 | 每个 pull request 的评论数 | Token（千） |
| --------------------- | -------------- | -------------- | -------------------------- | ----------- |

十个 pull request 里，专家组在七个上比单 agent 找到更多的 golden 发现，没有一个更少。榜单上召回率跟着评论数走：最好的 Codex 是 3.4 条评论 0.185，Devin 是 5.0 条 0.238，第一名是 5.4 条 0.260，精确率都在 0.84 到 0.90 之间。按相同的评论数来数，专家组和它们持平，并不领先；而且这个评判偏松：专家组没匹配上的 104 条评论里，它把 93 条判成了真问题。所以和榜单的比较要等用 Sonnet 5 评判的那次运行。

下面这些关于专家组自身的结论不受评判宽严的影响：

- 评论的排序在前面是对的，尾巴很长。每个 pull request 的前五条评论有 55% 能匹配上 golden 发现，第六到第十条是 25%，其余的是 15%，而其余的占全部评论的一半。
- 多个专家一致能预测匹配。两个以上专家报告的评论有 62% 匹配，只有一个专家报告的是 19%。
- 裁判的异议是有信息量的。被它质疑的 11 条评论没有一条匹配上 golden 发现，而它们现在仍然照常展示。
- 160 条评论里有 76 条是 nitpick，其中 16% 匹配。
- 相对单 agent 的提升在中等和低严重程度的发现上（0.55 对 0.38，0.27 对 0.09）。高严重程度的发现，专家组找到 11 条中的 5 条，单 agent 找到 6 条。

这些运行还发现了两个缺陷，都已修复并补了测试：diff 里有只改名不改内容的文件时，规划阶段会失败，因为 `@pulls.review/core` 要给这种文件算哈希，而内嵌运行时没有它调用的那个函数；没有发现的审查会把验证列表写成 `null`。
