# 评估

本页定义 eyeful 的评估实验。`eval/` 里的脚本已经写好；大部分 SWE-bench 被试、运行和标注还没有做（见[路线图](ROADMAP.md)）。结果等主实验跑完再补上。

## 研究问题 {#research-question}

与更简单的 LLM 审查者相比，带规划的多专家审查加上基于执行的验证，能否找到更多要紧的缺陷、噪声更少、并给出维护者可以核对的证据？代价是多少？

| 问题          | 问的是                                                                   |
| ------------- | ------------------------------------------------------------------------ |
| RQ1，检出     | 规划出的专家组是否比使用相同模型和 skill 的单个 agent 找到更多已知缺陷？ |
| RQ2，噪声     | 在每种验证条件下，报告的发现里有多大比例是可采取行动的？                 |
| RQ3，可验证性 | 执行能复现并修复多少发现，漏掉多少真实缺陷，代价是多少？                 |

## 数据集

一个被试是一个缺陷已知的改动。所有被试都来自公开的测试集，只有 SWE-bench 的测试能运行，所以 RQ3 只靠它回答。

| 数据集                     | 被试                                                   | 已知缺陷                   | 回答          |
| -------------------------- | ------------------------------------------------------ | -------------------------- | ------------- |
| SWE-bench Verified，回退版 | 从七个 Python 项目的 293 个任务里取约 30 个；已建 1 个 | 参考修复改动的那些行       | RQ1、RQ2、RQ3 |
| Code Review Bench，离线    | 五个项目的 50 个 pull request                          | 173 条人工审查者确认的评论 | RQ1、RQ2      |
| ReviewBench                | 219 个 pull request，187 个仓库，19 种语言             | 基准的 golden 发现         | RQ1、RQ2      |

- SWE-bench 被试把参考修复放进基准，再在改动里把它去掉。它用任务自带的 Docker 镜像构建，镜像名是中性的，issue 文本不提供，测试在没有网络的全新容器里运行。这七个项目是 `subjects.py` 有测试运行器的那些。
- ReviewBench 的 25 个测试 pull request 是 eyeful 开发时用的。留出部分按哈希从其余的里抽取，只在每次改动后检验一次；全集留给最后一次运行。
- 数据集放在 `.eval/` 下，被 git 忽略。被试的描述指明了缺陷，它和仓库分开存放，每次审查都在只能读取该仓库的沙箱里运行。早先的布局让 agent 能读到描述，那样做出的比较全部作废。

## 配置与条件

配置决定谁来找问题，条件决定发现怎样被验证。

| 配置   | 运行方式                             | 谁来审查                                                       |
| ------ | ------------------------------------ | -------------------------------------------------------------- |
| panel  | `eyeful review`                      | 规划器给改动分组，Go 挑选专家                                  |
| single | `eyeful review generalist`           | 一个拥有全部 skill 的 agent（见[名册](EXPERTS.md#the-roster)） |
| fixed  | `eyeful review correctness security` | 两个指定的专家，没有规划器，用于[消融](#ablations)             |
| revmux | `revmux.py`                          | 外部参照而不是基线：它的提示词不同                             |

| 条件      | 验证方式                                      |
| --------- | --------------------------------------------- |
| execution | 验证器运行每个复现，没有复现的发现由裁判阅读  |
| read-only | [裁判](VERIFICATION.md#the-judge)阅读每条发现 |
| none      | 发现按专家写的原样报告                        |

三种条件验证的是同一份发现存档，所以唯一的差别就是验证。没有测试命令时 execution 没有东西可跑，等同于 read-only，所以在 Code Review Bench 和 ReviewBench 上只比较 read-only 和 none。

## 流程

每个被试在每种配置下审查三次。execution 先跑，其他条件复用它的发现。失败的审查最多重试三次；agent 打开过仓库之外文件的审查记为 `leaked`，不计入。模型、提示词、预算和这份分析计划在主实验开始前固定。

## 指标与分析

| 问题 | 指标                                                                                                                                    | 分析                         |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| RQ1  | 召回率，各数据集的算法见下表；CWE 类别；每 token 的检出数                                                                               | 配置之间的 McNemar 精确检验  |
| RQ2  | 可采取行动的精确率，A / (A + N)，来自[标注](#labelling)                                                                                 | 以被试为单位的配对 bootstrap |
| RQ3  | 可验证率：通过全部六道[关卡](VERIFICATION.md#the-verifier)（含修复）的复现。验证损失：执行没能确认的可采取行动的发现。token、费用、秒数 | 以被试为单位的 bootstrap     |

| 数据集            | 已知缺陷算作找到的条件                              | 打分                    |
| ----------------- | --------------------------------------------------- | ----------------------- |
| SWE-bench         | 有发现落在它的文件上、距修复改动的行三行以内        | `analyze.py`            |
| Code Review Bench | 基准的裁判提示词判定某条发现就是那条 golden comment | `match.py`              |
| ReviewBench       | 基准的裁判把某条评论和那条 golden 发现配上          | 基准自己，或 `score.py` |

每个估计值都带 95% 区间，来自对整个被试的 10,000 次重采样。用 SWE-bench 自己的失败测试检查 eyeful 的修复，目前是手工做的。TODO(eval)：在 eyeful 的修复上运行任务的 `FAIL_TO_PASS` 测试。

## 标注 {#labelling}

不在已知缺陷上的每条发现由作者标注，每条不同的发现标一次。三点都成立时，它才是**可采取行动的**：

1. 问题确实以发现描述的方式存在于改动的代码里；
2. 是这次改动引入或暴露的；
3. 它改变了可观察的行为，或违反了明文约定。

其余都是**噪声**。裁判用的是同样的三点。

标注表以固定的随机顺序展示发现，不显示工具、配置和验证结果。五分之一的发现至少两周后再标一次，报告两次之间的 Cohen's κ。

## 消融实验 {#ablations}

去掉后测不出变化的部分，就从 eyeful 里去掉。

| 去掉的部分     | 运行方式     | 预期效果                           |
| -------------- | ------------ | ---------------------------------- |
| 规划器         | `fixed` 配置 | 混合改动上的召回率下降，或没有变化 |
| 判定依据的核对 | 从存档计算   | 更多发现成为阻塞，它们的精确率下降 |

## 效度威胁

- 所有发现都由一位作者标注。
- 基准用 Claude Sonnet 5 判分；主实验的模型和裁判还没有定，便宜的裁判更宽松。
- SWE-bench 的项目早于模型的知识截止，模型可能知道这个问题；在回退型被试上，被删的代码就在 diff 里。
- ReviewBench 的测试 pull request 就是调提示词用的那些。只有留出部分和全集给出可引用的数字。

## 工具 {#tooling}

`eval/` 里的脚本只用 Python 标准库，`plot.py` 和 `score.py` 除外，它们用 `uv run` 运行。`mise run test` 会运行它们的测试。

| 脚本             | 作用                                                                            |
| ---------------- | ------------------------------------------------------------------------------- |
| `subjects.py`    | 从 SWE-bench 的行或 Code Review Bench 的 golden comment 构建被试                |
| `reviewbench.py` | 构建 ReviewBench 被试，抽取留出部分，并把 eyeful 的评论写成基准的格式           |
| `run.py`         | 用 eyeful 审查每个被试：每种配置先找问题，然后各种条件做验证                    |
| `revmux.py`      | 用 revmux 审查每个被试                                                          |
| `confine.py`     | 在 macOS 沙箱里启动 pi，它只能读被审查的仓库，读不到用户的其他东西              |
| `audit.py`       | 列出审查者的 agent 在仓库之外打开过什么                                         |
| `match.py`       | 按 Code Review Bench 离线流程的方式给审查打分                                   |
| `score.py`       | 用 [Jev](ARCHITECTURE.md#jev) 把 eyeful 的评论和 ReviewBench 的 golden 发现配对 |
| `plot.py`        | 把 eyeful 画在 ReviewBench 排行榜旁边                                           |
| `label.py`       | 写出盲标注表并计算 κ                                                            |
| `analyze.py`     | 根据审查和标注计算各项指标                                                      |
