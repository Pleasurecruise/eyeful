# 效果评测

本页属于毕业设计，定义了回答研究问题的实验，实验结果也是对外公布的 eyeful 数据。实验在 v1.0 的研究核心上进行，在开发其他客户端之前完成（见[版本路线图](ROADMAP.md)）。代码会放在 `eval/` 下，用 Python 编写，目前还没有写。下面三种实验条件已经是 `workflow` 的一个设置项。

## 研究问题 {#research-question}

对于可以复现的发现，和只读验证相比，带外部判定依据的执行验证能去掉多少误报？代价是多少 token、多少钱、多少时间？

问题只针对可复现的发现，也就是 correctness 和 security 专家给出、并附带复现测试的发现。design 和 readability 的发现从来不会被执行，算进来只会冲淡效果。这里的“执行验证”指[证据与验证](VERIFICATION.md)中描述的验证器，包括判定依据规则。

## 实验条件

主实验是在 eyeful 内部做的消融，每种条件下提示词、改动的切分方式和模型都相同：

| 条件      | 专家和模型 | 验证方式                                    |
| --------- | ---------- | ------------------------------------------- |
| execution | 相同       | 验证器运行每个复现，强度取决于判定依据      |
| read-only | 相同       | 由一个评判 agent 读代码和每条发现，给出结论 |
| none      | 相同       | 不验证，按专家写的原样报告                  |

每次审查通过 `Request.Verification` 选择条件：`execution`、`read_only` 或 `none`。

revmux 的验证阶段也是只读的，它会在同样的数据上运行，作为外部参照，但不作为基线：它的提示词和切分方式与 eyeful 不同，这些差异会混进结果里。

## 数据集

| 数据集                    | 用途                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 注入 bug 集               | 主要数据集。bug 注入到模型训练截止日期之后的仓库和提交中，模型不可能见过                                            |
| SWE-bench Verified 回滚集 | 次要数据集。真实的 bug，附带能证明它的测试，在 SWE-bench 自带的 Docker 环境中运行。模型可能在训练中见过，论文会说明 |
| Code Review Bench 离线集  | 按专家统计召回率和精确率，与现有审查工具比较                                                                        |

前两个数据集中，每个样本都有一个已知的 bug。这个 bug 有没有找到不需要人工标注，但专家报告的其他发现都需要。

## 标注

计算精确率需要把每条额外的发现标为真实问题或误报。标注由作者本人完成，依据一份书面的标注指南（放在论文附录），指南写明什么算真实问题。三种条件下的发现混在一起随机打乱，标注时看不到来自哪种条件。大约 20% 的发现在至少两周后再标一次，用两次之间的 Cohen's κ 报告标注者自身的一致性。每种条件大约标注 150 到 200 条发现。论文会把只有一名标注者列为局限，并说明上述措施。

## 消融实验 {#ablations}

工作流的每个部分都要证明自己有用：去掉它，重新跑一遍，看哪些指标下降。

| 去掉的部分                           | 预期结果                           | 比较用的数据集    |
| ------------------------------------ | ---------------------------------- | ----------------- |
| 执行验证（主要结果）                 | 可复现发现的精确率下降             | 两个 bug 数据集   |
| 判定依据规则（任何失败的测试都算强） | 精确率下降                         | 两个 bug 数据集   |
| 按需启动（每次改动运行所有专家）     | 召回率不变，成本和时间上升         | Code Review Bench |
| 规划器（所有档位都用规则分派）       | 混合型改动的召回率下降，或没有变化 | Code Review Bench |
| 汇总（改用规则排版）                 | 反馈没那么好用，或没有变化         | Code Review Bench |
| 分诊（所有文件都交给专家）           | 召回率不变，成本上升               | Code Review Bench |
| CI 校验                              | 召回率不变，成本上升               | Code Review Bench |
| 专家之间互不可见                     | 每个专家的独有发现减少             | 注入 bug 集       |
| 依次去掉每个专家                     | 该专家负责类别的召回率下降         | Code Review Bench |

去掉之后没有任何可测量变化的部分，就从 eyeful 中删掉。

## 指标与成本

指标包括：已知 bug 的召回率、已标注发现的精确率、规划器的准确率、修复建议的通过率，以及每次审查的 token 数、费用和耗时。成本只在 pi 上测量，因为那里的模型调用由 eyeful 发起和计数。本地审查用的是用户自己的订阅，而且不是每个命令行工具都报告费用，所以不纳入实验。

所有数字都来自运行归档。每次审查的归档里有每个 agent 的提示词、输出、工具调用、模型和 token 数，以及每次验证运行的命令、退出码和耗时。运行归档属于 v1.0 的研究核心，没有它就没有数据。
